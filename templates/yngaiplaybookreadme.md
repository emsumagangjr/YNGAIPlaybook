# .yngaiplaybook

> Generated by `yngorch` from YNGAIPlaybook {{VERSION}}. Edits to this
> file are replaced on the next install; the other files here are yours
> to keep as described below.

This folder holds the YNGAIPlaybook files for this project. It sits in
the project root, beside `.bare/`, outside every worktree, and is never
committed: no branch or pull request can change what is in it.

## Layout

``` text
.yngaiplaybook/
├── README.md                       this file
├── yngorchestratorconfig.yml       your settings for /yngorchestrator: provider and host, issues repo, Gate 1, Gate 2
├── yngorchestratorconfig.yml.bak   your settings as they were before the last install added to them
└── yngorchestratorruns/
    ├── <epic>.md                   run log, one per Epic or standalone issue
    └── <n>.lock                    run lock, present while a run writes issue state
```

## Naming

Every item here is named `<tool><purpose>`, with no separator
(`yngorchestratorconfig.yml`, `yngorchestratorruns/`), so tools sharing
the folder cannot collide. A future playbook feature that keeps files in
the project root puts them here, named the same way, and gets its own
section below.

### The settings in `yngorchestratorconfig.yml`

The config tells the orchestrator which decisions it may take on its own
and which stay with you. It is yours: edit it by hand. `yngorch` writes
it whole from the playbook's template only when it is absent. On a
reinstall it keeps every setting you have and adds only what the
template has and your file lacks: a missing setting, with its comments,
just above the worked examples; a missing key under a setting active in
your file, such as a new `merge:` path. It never changes, removes or
reorders a line of yours. Before adding anything it copies the file to
`yngorchestratorconfig.yml.bak` beside it, replacing an older backup,
and prints a `backed up` line and one `added` line per setting or key;
with nothing to add it writes no backup and prints
`kept .yngaiplaybook/yngorchestratorconfig.yml (yours, nothing new)`.
A setting whose header you kept, with its key commented out, stays as
you left it; one you deleted, header and key, comes back at its
default. A key it cannot add line by line (its parent's value written
on the parent's own line, the parent set twice, or the keys under it
indented with a tab or unevenly) is a `warning` giving the line to
paste by hand. A key of yours the template does not have stays as it
is, with a `note` that the orchestrator ignores it. The other writes
fill in `provider:` and `host:` when they have no value, and an empty
`issues:` when you pass `-IssuesRepo`. No branch
or pull request can change it. The
orchestrator reads it as it is now, at the start of every run and again
before every merge, so an edit counts from the next read. A missing file
means every default below. The file itself explains each setting the
same way.

Gate 1 is the decision that an issue is ready for an agent to start
(its mark is the label `workflow:ready-for-agent`); Gate 2 is the
decision to merge a pull request. An Epic is one feature, built on an
`epic/*` branch out of smaller issues called slices, each merged into
the Epic branch through its own pull request. The plan is the table of
slices the orchestrator proposes for an Epic, for you to approve before
any slice is created.

| Key | Decides | Values | Default, absent or unknown | Read | Changed by |
|-----|---------|--------|----------------------------|------|------------|
| `provider:` | Which git provider holds the repository, and so which tool the orchestrator works through (not a gate). | `github` (`gh`), `gitlab` (`glab`), or `bitbucket` (Bitbucket Cloud, through its REST API with `curl`, `BITBUCKET_EMAIL` and `BITBUCKET_API_TOKEN`; the token stays in your environment, never in this folder). | `github`. Absent or empty: `github`, so an older config works as before. Any other value stops the run before it touches anything, and stops `yngorch`. | Start of every run | You. `yngorch` writes it only when it has no value yet, never over a value: detected from `origin`'s host, or from `yngorch -Provider` (`--provider` in `yngorch.sh`) when it cannot tell. A `-Provider` that differs from your value is a warning, and your value is kept. |
| `host:` | The provider's host, such as a GitHub Enterprise Server or GitLab self-managed host (not a gate). | `<host>`, without `https://`. Bitbucket takes only `bitbucket.org`: Bitbucket Data Center is planned, not supported, and `yngorch` stops on it. | No value: the provider's cloud host, `github.com`, `gitlab.com` or `bitbucket.org`. | Start of every run | You. `yngorch` writes it only when it has no value yet, from `origin`'s URL (else the provider's cloud host), never over a value. |
| `issues:` | Where this project's issues live (not a gate). Code, branches and pull requests stay in `origin`'s repository. | `<owner>/<repo>`: the issues live in that GitHub repository. No value: they live in `origin`'s repository. | No value. Absent, empty, or `origin`'s own repository: the default. A value that is not `<owner>/<repo>` stops the run before it touches anything, and `yngorch` skips the labels with a warning. | Start of every run | You. `yngorch -IssuesRepo <owner>/<repo>` (`--issues-repo` in `yngorch.sh`) writes it only when it has no value yet, never over a value. `yngorch` adds the setting, commented out, when it is missing. |
| `auto-promote:` | Gate 1 in advance, for the slices the orchestrator plans for an Epic. | `no`: you promote each slice (label `workflow:ready-for-agent`). `yes` (or `true`, any case): approving the Epic's plan promotes the slices it routes to an agent, and work starts at once. | `no`. Absent, or any value other than `yes` or `true`: `no`. Under any value, a slice only a person may do, a standalone issue and a slice created by hand still need your label. Switching back to `no` undoes earlier plan promotions. | Start of every run | You. `yngorch` adds the key, at `no`, when it is missing, and never changes it. |
| `merge:` `slice-to-epic:` | Gate 2 in advance for a slice's pull request (`slice/*`) into its Epic branch. | `required`: you merge. `auto`: the orchestrator merges once the agent reported the work done, the pull request is open and mergeable between the expected branches, every check passed and its review record holds no open decision; otherwise it stays with you, with a comment naming why. | `required`. Absent, or any value other than `auto`: `required`. | Before every merge | You. `yngorch` adds it, at `required`, when it is missing, and never changes it. |
| `merge:` `epic-to-main:` | Gate 2 in advance for an Epic's pull request (`epic/*`) into `main`, which delivers the feature. | As `slice-to-epic:`, and `auto` also waits until every slice issue of the Epic is closed. | `required`. Absent, or any value other than `auto`: `required`. | Before every merge | You. `yngorch` adds it, at `required`, when it is missing, and never changes it. |
| `merge:` `fix-to-main:` | Gate 2 in advance for a standalone fix's pull request (`fix/*`) into `main`: an issue worked alone, with no Epic. | As `slice-to-epic:`. | `required`. Absent, or any value other than `auto`: `required`. | Before every merge | You. `yngorch` adds it, at `required`, when it is missing, and never changes it. |

#### Example: the default, every gate with you

``` yaml
auto-promote: no
merge:
  slice-to-epic: required
  epic-to-main: required
  fix-to-main: required
```

The run stops for you to approve the Epic's plan; promote each slice
before an agent starts it, then run the orchestrator again; do the
slices only a person may do; answer open decisions in a pull request's
review record; merge every pull request; and take over a slice that
failed twice.

#### Example: hands-off, plan approval carries the Epic

``` yaml
auto-promote: yes
merge:
  slice-to-epic: auto
  epic-to-main: required
  fix-to-main: required
```

The run still stops for you to approve the Epic's plan (that approval
promotes its agent slices, and work starts at once); do the slices only
a person may do, while the slices that depend on them wait; answer open
decisions in a pull request's review record, since such a pull request
is not merged; merge a slice's pull request that fails a merge
condition, such as a failed check or a conflict; merge the Epic into
`main`, since `epic-to-main` stays `required`; and take over a slice
that failed twice.

A lock left by a crashed run stays until you delete it; the orchestrator
never deletes a lock it did not create.
